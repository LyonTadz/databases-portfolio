4 · ROUND 4 — PLANS AND EQUALITY (timings live in bench.py)
==============================================================================
  NO TIMINGS ON THIS PAGE. bench.py is the only harness that reports
  milliseconds, and the reason is a result in itself: when I timed the same
  two queries from inside this script — which rebuilds a 200k table and runs
  dependency checks over it first — arm A's minimum moved from 75 ms to 95 ms
  between two phases that do not touch arm A at all. The effect being measured
  is 20 ms. Timing inside a process that is also doing other work measures the
  other work. Run bench.py on its own; across three consecutive runs it gives
  phase-1 ratios of 1.02-1.04, phase-2 of 1.46-1.48, and — after one ANALYZE —
  0.73-0.75, i.e. the NORMALIZED design winning. See benchmark.md section 4.
  What belongs here is everything that is NOT a clock reading:

-- 4.1 the two designs return the same answer --------------------------------
  rows: A=350  B=350
  total cost: A=722610.0  B=722610.0
  row-for-row identical: True
  -> a like-for-like comparison of two designs, not of two questions.

-- 4.2 the plans, with ix_report_machine present -----------------------------
  A normalized:
      SCAN jp
      SEARCH j USING INTEGER PRIMARY KEY (rowid=?)
      SEARCH m USING INDEX sqlite_autoindex_machine_1 (machine_id=?)
      SEARCH p USING INDEX sqlite_autoindex_part_1 (part_no=?)
      USE TEMP B-TREE FOR GROUP BY
  B denormalized:
      SCAN report_jobpart USING INDEX ix_report_machine
      USE TEMP B-TREE FOR GROUP BY
  note B: SCAN ... USING INDEX on a query with no WHERE on machine_id and no
  ORDER BY. The index filters nothing; it walks all 200,000 entries and then
  fetches every row by rowid. In a plan, SEARCH skips rows and SCAN does not.

-- 4.3 the plan after dropping the index — the whole Round 4 finding ---------
  B denormalized, no index:
      SCAN report_jobpart
      USE TEMP B-TREE FOR GROUP BY
  same answer still: True  (350 rows, 722610.0)
  index restored.

-- 4.4 why the join is nearly free: the size of what A probes ----------------
  job_part    200000 rows      3328.0 KB
  job          20000 rows       640.0 KB
  machine         50 rows         4.0 KB
  part            10 rows         4.0 KB
  the dimensions are 4 KB each and permanently in cache, so A's 600,000
  B-tree probes cost almost nothing. The scan and the GROUP BY cost everything.

6b · ROUND 6 — COST OF EACH STALENESS STRATEGY
==============================================================================
  (running on a throwaway copy; normalize.db is not touched)

-- 6b.1 scheduled rebuild — how long a full rebuild of 200,000 rows takes ----
  CREATE TABLE … AS SELECT (200,000 rows)  min    115 ms   median    118 ms
  CREATE INDEX on the result               min     57 ms   median     58 ms
  full rebuild from scratch                min    172 ms
  -> against a dashboard that refreshes every 30 s, a full rebuild is a
     0.57% duty cycle. The copy can simply be rebuilt.

-- 6b.2 trigger-maintained copy — per-insert overhead ------------------------
  without trigger    1.38 us per job_part insert (min of 5 batches of 300)
  with trigger       3.92 us per job_part insert (min of 5 batches of 300)
  overhead: 2.83x, i.e. 2.54 us per row
  rows the trigger wrote: 300
  -> cheap per insert. The problem is not the cost, it is the coverage:

-- 6b.3 why one trigger is not enough — what the copy depends on -------------
  report_jobpart denormalizes columns from FOUR tables:
    job_part -> the fact itself      (INSERT / DELETE)
    job      -> technician, done_on  (INSERT / UPDATE / DELETE)
    machine  -> site                 (UPDATE)
    part     -> part_price           (UPDATE)
  so keeping it correct needs a trigger on each, for each DML verb that can
  change a copied column. A trigger on job_part alone cannot see a site
  change at all — Round 5 measured that update as 4,000 rows in the copy.
  Module 4 found the matching failure directly: an AFTER INSERT trigger does
  not fire on the ON CONFLICT DO UPDATE path, so a corrected row silently
  skips maintenance. ~8 triggers to keep one copy fresh, against a sub-200 ms
  rebuild (see 6b.1), is the whole argument for the rebuild.

-- 6b.4 materialized views in SQLite -----------------------------------------
  CREATE MATERIALIZED VIEW -> OperationalError: near "MATERIALIZED": syntax error
  SQLite has plain views only: a VIEW re-runs its SELECT on every read, so it
  is the normalized query with a nicer name — zero staleness, zero speed-up.
  'Materialized view' in this module means 'a table you rebuild yourself'.
  verification that the copy and the join agree, which any strategy needs:
    report_jobpart EXCEPT the join -> 0 rows (in sync)

  normalize-staleness.db removed. normalize.db is still 35.4 MB, as setup.sql built it.
