# Module 5 · Stretcher — the same question in DuckDB

[← Round 7 harvest](./harvest.md) · [Module 5 home](./README.md) · [Round 4 benchmark](./benchmark.md)

The ◇ stretcher asks: load the same data into DuckDB, run the dashboard query,
and note whether the columnar engine removes the need for the denormalized table
entirely. Generated by [`evidence.py`](./evidence.py) §7.

> **Short answer: yes, and for a reason I did not expect.**
>
> DuckDB runs the **normalized four-way join in 8.86 ms**. The best SQLite could
> do with the **denormalized** table, index dropped and statistics collected, was
> 37.0 ms. So the engine change makes the correct schema **4.2× faster than the
> compromised one was** — and the whole point of `report_jobpart` was to buy a
> speed-up that this measures at 5%.
>
> But *inside* DuckDB, denormalizing still helps by **1.87×**. The need goes away
> because of the absolute numbers, not because the trade-off stops existing.

---

## 1 · Getting the data in

```python
# the one-liner, if your machine can reach extensions.duckdb.org:
d.execute("INSTALL sqlite; LOAD sqlite;")
d.execute("ATTACH 'module-05/normalize.db' AS s (TYPE sqlite, READ_ONLY)")
```

That failed in my sandbox — `IOException: Failed to download extension
"sqlite_scanner"`, because the environment has no route to
`extensions.duckdb.org`. So [`evidence.py`](./evidence.py) exports the five tables
to CSV and reads them back with `read_csv_auto`, which needs no extension. If you
can reach the internet, use `ATTACH`; it is one line and avoids a round trip
through text.

Going through CSV turned up something worth keeping, though:

```
done_on arrived as: DATE
```

`read_csv_auto` **inferred a real `DATE` type** from the text. In SQLite the same
column is `TEXT`, because SQLite has no date type at all — `date('2026-03-01')`
returns a string and `done_on >= date(...)` is a *string* comparison that happens
to work because ISO-8601 sorts correctly as text. That is the same class of
problem as `part_price` being `TEXT` ([harvest](./harvest.md) §1): SQLite leans on
lexicographic order matching semantic order, and it does for ISO dates and does
not for decimal numbers.

## 2 · The query needed two edits, and one of them is a finding

```diff
- WHERE j.done_on >= date('2026-03-01')
+ WHERE j.done_on >= DATE '2026-03-01'

- GROUP BY m.machine_id, j.technician
+ GROUP BY m.machine_id, m.site, j.technician
```

The second edit is not cosmetic. DuckDB **refuses** the original:

```
BinderException: column "site" must appear in the GROUP BY clause
or must be part of an aggregate function.
```

SQLite accepts `m.site` in the select list without grouping by it and silently
picks a value from an arbitrary row of each group. Here that is harmless — the
query groups by `machine_id` and `machine_id → site`, so every row in a group has
the same site. But **the engine does not know that**, and it did not check: if I
had selected `technician` while grouping only by `machine_id`, SQLite would have
returned one technician per machine with no warning, and the dashboard would have
been quietly wrong.

So the functional dependency from [Round 1](./normalization-notes.md) is the only
reason the SQLite query is correct, and nothing in the SQL says so. DuckDB
rejecting it is the stricter engine catching a dependency assumption I had not
written down — which is the Module 5 theme arriving from an unexpected direction.

## 3 · The numbers

DuckDB 2.0.1, two threads, 9 interleaved repetitions, minimum estimator — same
method as [Round 4](./benchmark.md).

| Arm | min (ms) | median (ms) |
|---|---|---|
| A — normalized, 4-way join | 8.86 | 9.78 |
| B — denormalized, 1 table | **4.75** | 4.95 |

**A/B = 1.87×.** Both return 350 rows totalling 722,610.0 — the same answer
SQLite gives.

### 3.1 Is it just the extra core?

```
threads=1:  A min 11.58 ms,  B min 6.92 ms,  ratio 1.67x
```

No. Single-threaded DuckDB still runs the four-way join in **11.58 ms** against
SQLite's 38.9 ms best, so **3.4× of the gap is the engine itself** and the second
thread contributes about 1.31×. Columnar storage, vectorized execution and hash
joins instead of per-row B-tree probes do the work; parallelism is a bonus.

### 3.2 Everything side by side

| Engine | Design | Configuration | min (ms) |
|---|---|---|---|
| SQLite | normalized | as built | 55.3 |
| SQLite | denormalized | as built | 53.3 |
| SQLite | denormalized | index dropped | 37.6 |
| SQLite | normalized | `ANALYZE`'d | 39.8 |
| SQLite | **denormalized** | **`ANALYZE`'d, index dropped — best SQLite** | **37.0** |
| DuckDB | normalized | 1 thread | 11.58 |
| DuckDB | **normalized** | **2 threads** | **8.86** |
| DuckDB | denormalized | 2 threads | 4.75 |

Read the two bold rows. **The best SQLite can do with a denormalized schema is
4.2× slower than DuckDB managing the normalized one.** Everything the whole
module measures — the index, the statistics, the join count, the duplicated
columns — moves the needle less than the choice of engine.

## 4 · So why does denormalizing help *more* in DuckDB?

This is the part I had to think about, because it is the opposite of what I
expected. In SQLite, with both designs configured properly, denormalizing bought
**1.05×**. In DuckDB it buys **1.87×**.

The reason is that the ratio is not a measure of how expensive the join is — it
is the join's share of a *total that got much smaller*. DuckDB's scan and
aggregate are perhaps 6× faster than SQLite's, but its hash joins over 200,000
rows are not 6× faster than SQLite's cache-resident B-tree probes, which were
already nearly free. Shrink the denominator and the same absolute join cost
becomes a bigger fraction.

In absolute terms denormalizing saves **4.1 ms** in DuckDB and **1.9 ms** in
SQLite. Neither is worth a maintenance burden; the DuckDB one just looks more
impressive as a percentage.

**The trap this points at:** "denormalization gave us 1.87×" would be a perfectly
defensible sentence to put in a report, and it would be describing a 4-millisecond
saving on a query that got 4× faster for an unrelated reason. A ratio without its
absolute numbers is not a finding. That is the same lesson as
[Round 4](./benchmark.md) §1 in a different coat: there I needed the minimum to
know whether a difference was real, here I need the absolute time to know whether
a real difference matters.

## 5 · What this means for the memo

It changes the recommendation. If the dashboard is genuinely too slow, the
ordered list of things to try is:

1. **`ANALYZE`** — 77 ms, one command, no schema change, 1.39× on the normalized
   query.
2. **Drop the index that is not filtering** — one command, *less* storage.
3. **Move the read path to a columnar engine** — 4×, no change to the
   transactional schema, which stays in 3NF and keeps its guarantees.
4. **Denormalize** — 5%, in exchange for 1.72× the storage and a 4,000-row write
   where there was a 1-row write.

Denormalization is last on that list, and it is the only item that gives something
up. This is also the bridge into **Module 6a**: the Parquet/columnar path is not
a different answer to the same question, it is what makes the question stop
mattering.
